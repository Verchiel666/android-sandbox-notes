摘要沙箱实测linker64 机制zygote 身份源码怎么拿到手机上

摘要

一台不 root 的 Android 手机，一个普通 App 到底能跑什么、不能跑什么？答案不在编译器、也不在文件权限，而在三件事：它的文件落在哪个 SELinux 类型、它是被谁 fork 出来的（哪些 MLS 类别）、以及 它能不能碰到系统 socket。

本文所有结论都有两处证据：AOSP 源码（bionic / system/core / frameworks/base 快照）里的具体行号，以及这台手机上的实测输出（错误码、SELinux 上下文、/proc 状态）。文中标注了源码快照（≈Android 15/16）与本机（Android 17）的差异。

能力结果原因
跑自己目录里的 ET_DYN 动态二进制✅SELinux 拦 execve，不拦 mmap
跑静态 / ET_EXEC 二进制❌bionic linker 只收 ET_DYN
fork/exec 子进程（git 的 https helper、pip…）❌子进程 execve 撞 app_data_file 的 entrypoint
读别的 App 数据 / 系统 sealed 文件❌类型 + MLS 类别
连系统 socket（zygote、property_service…）❌660 root:system + socket 标签 + peer cred
借 Shizuku 以 shell 身份跑原生程序✅shell 域对 shell_data_file 有 entrypoint

一 · 沙箱实测

设备：荣耀 Magic8 RSR 保时捷设计（BKQ-AN20，SM8850），Android 17 / SDK 37，kernel 6.12.58，aarch64 身份：普通 App，uid 10104，targetSdk 34；辅助身份：Shizuku 提供的 shell（uid 2000） 方法：AOSP 源码（frameworks/base、system/core、bionic 快照）+ 本机实测，两边对齐

三层的沙箱把答案写死了：SELinux entrypoint（能不能执行）、zygote 一次 fork 定死的身份（你是谁）、 init 发出去的 socket 权限模型（能跟谁说话）。

第一层｜execve 被拒，但 linker64 能跑

排除法：不是文件属性，也不是挂载

检查 结果
私有 ELF 权限 -rwxr-xr-x，属主就是自己
/data 挂载 f2fs rw,seclabel,nosuid,nodev —— 没有 noexec
直接执行 Permission denied（EACCES）

真正的原因：SELinux file:entrypoint

文件 SELinux 类型
/system/bin/linker64 system_linker_exec（专门的类型）
/system/bin/sh shell_exec
App 私有目录、libdshnode.so app_data_file

App 对前两种类型有 entrypoint 权限，对 app_data_file 没有 → execve 直接被内核拒绝。

为什么 linker64 <file> 可以：加载 ≠ 执行

bionic 的 linker 本来就是"解释器"角色，它支持的用法里明确写了直接跑：

  • bionic/linker/linker_main.cpp:790-823
    // When the linker is run directly rather than acting as PT_INTERP, parse
// arguments and determine the executable to load. ...
exe_to_load = args.argv[1];
    官方 usage："This program can also be run directly to load and run a dynamic executable."
  • 它用 mmap + mprotect(PROT_EXEC) 把我们的文件映射进来（linker_phdr.cpp:597-705），走的是 file:execute——和 App 加载自己的 .so 是同一条权限路径，不触发 entrypoint 检查。

代价：只能跑 ET_DYN（PIE）

bionic/linker/linker_phdr.cpp:292-294：

if (header_.e_type != ET_DYN) {
  DL_ERR("\"%s\" has unexpected e_type: %d", ...);

实测 linker64 librg.so（ET_EXEC 全静态）→ has unexpected e_type: 2，与源码逐字对上。

依赖库要自己给路径

linker64 jq            → CANNOT LINK EXECUTABLE: library "libjq.so" not found
LD_LIBRARY_PATH=... bin → jq-1.8.2

（同理，libdshnode.so 靠编译期 RPATH=$ORIGIN 找到 82 MB 的 libnode.so。）

推论：任何需要 fork/exec 子进程的工具（git 的 git-remote-https、pip、多进程 CLI）在 App 身份下 结构性不可行，因为子进程的 execve 会再撞一次 app_data_file 的 entrypoint 限制。

第二层｜App 的沙箱身份是 fork 时一次定死的

源码链路

  1. system/core/rootdir/init.zygote64.rc:1： service zygote /system/bin/app_process64 --zygote ...，socket zygote stream 660 root system —— 此刻是 root + zygote 域（本机实测：zygote64 PID 4337，user=root，label=u:r:zygote:s0）。
  2. frameworks/base/cmds/app_process/app_main.cpp:79 → ZygoteInit → 每个 App 由 forkAndSpecialize() 生出。
  3. frameworks/base/core/jni/com_android_internal_os_Zygote.cpp 里依次做完：
行号 动作 意义
552 setgroups(...) 附加组
2010 SetUpSeccompFilter(uid, …) 装 seccomp 过滤器
2001 / 2015 setresgid / setresuid 换成 App 的 uid
2133 selinux_android_setcontext(uid, is_system_server, se_info, name) 切 SELinux 域

域从哪来（本机文件，一手）

/system/etc/selinux/plat_seapp_contexts:41（App 读不到，adb_shell 能读）：

user=_app minTargetSdkVersion=34 domain=untrusted_app_34 type=app_data_file levelFrom=all

我们的进程 /proc/self/attr/current = u:r:untrusted_app_34:s0:c104,c256,c512,c768：

  • minTargetSdkVersion=34 命中（本 App targetSdk 34）
  • type=app_data_file —— 就是第一层 execve 被拒用的类型
  • levelFrom=all 生成 c104,c256,c512,c768 这串 MLS 类别：同 App 的文件只有同类别能读，是隔离的另一半

seccomp 在，但不是拦路的那位

/proc/self/status：Seccomp: 2、Seccomp_filters: 1（过滤器已生效）。 但 exec 返回的是 EACCES（SELinux），不是 seccomp 的 EPERM —— 两者可以据此区分。

一处处"文档对不上本机"

A15 源码里策略来自文本文件 /system/etc/seccomp_policy/app.arm64.policy； Android 17 上该文件不存在，实际提供者是 /system/lib64/libseccomp_policy.so（36 KB， 导出符号 set_app_seccomp_filter）——策略从文件搬进了 so。

第三层｜socket 权限模型：谁能和谁说话

init 发 socket 时定了三件事

system/core/init/util.cpp:95 CreateSocket(name, type, passcred, listen, perm, uid, gid, socketcon)：

  1. setsockcreatecon(socketcon) —— 创建时就指定 socket 的 SELinux 标签；
  2. SelabelLookupFileContext + setfscreatecon —— 按 file_contexts 给 socket 节点打标签；
  3. SO_PASSCRED —— 接收端可拿到对端 uid/gid/pid（SCM_CREDENTIALS），用于身份核对。 调用方 init/service_utils.cpp:199 把 .rc 里的 perm/uid/gid 传进去。

本机实测

  • .rc：socket zygote stream 660 root system（另有 zygote_next seqpacket 660 root system）
  • /system/etc/selinux/plat_file_contexts：/dev/socket/zygote u:object_r:zygote_socket:s0
  • /proc/net/unix 里确有 /dev/socket/zygote
  • 代价是连 stat 都不给：ls -l /dev/socket 列出 59 个条目，socket 文件那一批全是 s?????????（stat 被拒）；App 或 shell 直接 ls -l /dev/socket/zygote → Permission denied

所以一个普通 App 想"假装"和 zygote/servicemanager 通信，会在权限位、SELinux 标签、peer cred 三关里任一关被挡下；这也是第三方 App 无法劫持系统 socket 的底层原因。

结论：能做 / 不能做（对无 root 的 App 成立）

能力 结果 依据
加载并运行自己目录里的 ET_DYN 动态二进制 ✅ 可以（/system/bin/linker64 <路径>） SELinux 只拦 execve，不拦 mmap
跑静态 / ET_EXEC 二进制 ❌ bionic 只收 ET_DYN
fork/exec 子进程（git 的 https helper、pip…） ❌ 子进程 execve 撞 entrypoint
读自己 App 的数据文件 ✅ 同 MLS 类别 c104,…
读别的 App 数据、系统 sealed 文件（seapp_contexts 等） ❌ 类型 + 类别
连系统 socket（zygote、property_service…） ❌ 660 root:system + zygote_socket 标签
借 shell（Shizuku）跑任意 aarch64 原生程序 ✅ shell 域对 shell_data_file 有 entrypoint

一句话：这台手机上"能不能跑某个程序"不是编译器问题、不是权限位问题，而是 它落在哪个 SELinux 类型 + 哪些 MLS 类别 + 由谁 fork 出来。

二 · linker64 为什么能跑（源码依据）

日期：2026-11-06　源码：$HOME/work/aosp-src/bionic（aosp-mirror，main）

一句话

execve 被拒是 SELinux 的 file:entrypoint（目标类型 app_data_file 不给 app 当入口点）； 能跑是因为 /system/bin/linker64 的类型是专门的 system_linker_exec，它作为"解释器"去 mmap + mprotect(PROT_EXEC) 我们的文件（这属于 file:execute，app 对自己的 data 目录是允许的）。

本机实测（有编号，可复现）

观察 结果
私有文件模式 -rwxr-xr-x（0755），uid 就是我们自己
/data 挂载选项 f2fs rw,...,seclabel,nosuid,nodev —— 没有 noexec，排除 mount 因素
直接跑 .../usr/bin/jq Permission denied（EACCES）
linker64 .../jq（不带 LD_LIBRARY_PATH） CANNOT LINK EXECUTABLE ...: library "libjq.so" not found ⇒ 已经进入 bionic 加载阶段，说明 mmap 成功
LD_LIBRARY_PATH=.../lib linker64 .../jq jq-1.8.2（正常输出）
linker64 $HOME/../bin/rg has unexpected e_type: 2（rg 是 ET_EXEC 全静态）

SELinux 类型（ls -Z / getenforce = Enforcing）：

  • u:object_r:system_linker_exec:s0 /system/bin/linker64
  • u:object_r:shell_exec:s0 /system/bin/sh
  • u:object_r:app_data_file:s0:c104,c256,c512,c768 ← 我们的私有目录、tbins prefix、APK 解出来的 libdshnode.so

bionic 源码依据

  1. 只收 ET_DYN：linker/linker_phdr.cpp:292-294
    if (header_.e_type != ET_DYN) {
  DL_ERR("\"%s\" has unexpected e_type: %d", name_.c_str(), header_.e_type);
  return false;
}
    ET_EXEC = 2 ⇒ 静态/PIE 之外的二进制一律被拒，和 librg.so 的实测报错逐字对应。
  2. 支持"直接当加载器跑"：linker/linker_main.cpp:790-823
    // When the linker is run directly rather than acting as PT_INTERP, parse
// arguments and determine the executable to load. ...
exe_to_load = args.argv[1];
    官方 usage 字符串也写着："This program can also be run directly to load and run a dynamic executable." 所以 /system/bin/linker64 <elf> 是受支持用法，不是野路子。
  3. 加载过程走 mmap + mprotect(PROT_READ|PROT_WRITE)（linker_phdr.cpp:597-705）， 与我们观察到的"同目录 .so 能加载、execve 不能"一致：前者是 execute，后者要 entrypoint。

对我们的影响

  • 私有目录里的工具必须是 ET_DYN（PIE）+ bionic 动态链接；静态/ET_EXEC 无解（除非走 shell 身份）。
  • 依赖库必须让 linker 找得到：LD_LIBRARY_PATH=<prefix>/lib（dsh-termux/tb 包装器自动设）， 或编译时带 RPATH=$ORIGIN（libdshnode.so 就是这么找到 libnode.so 的）。
  • 需要 exec 子进程的工具（git 的 git-remote-https、python 的 pip 等）根本走不通： 子进程 execve 仍然撞 app_data_file 的 entrypoint 限制 —— 这正是 git 只能以 shell 身份跑的原因。

三 · App 进程怎么变成 untrusted_app_34

日期：2026-11-06　源码：$HOME/work/aosp-src（A15 快照）　设备：Android 17 / 无 root

一、源码里的链路（带行号）

  1. init 起 zygote：system_core/rootdir/init.zygote64.rc:1 service zygote /system/bin/app_process64 -Xzygote /system/bin --zygote --start-system-server --socket-name=zygote 第 6 行 socket zygote stream 660 root system。此时进程是 root + zygote 域，不是 app。
  2. app_process 是入口：frameworks_base/cmds/app_process/app_main.cpp:79 AppRuntime::onStarted() → 启动 com.android.internal.os.ZygoteInit，之后由 Java 侧 Zygote.forkAndSpecialize() 逐个 fork。
  3. 每个 app 进程的降权顺序（frameworks_base/core/jni/com_android_internal_os_Zygote.cpp）：
行号 动作
552 setgroups(...) 设置附加组
2010 SetUpSeccompFilter(uid, is_child_zygote) ← 先装 seccomp
2001 / 2015 setresgid / setresuid ← 换成 app uid（如 10104）
2133 selinux_android_setcontext(uid, is_system_server, se_info, nice_name) ← 切 SELinux 域

sandbox 三件套 = uid + seccomp + SELinux 域，一次 fork 里全部完成。

二、域是怎么选出来的（本机文件，一手）

/system/etc/selinux/plat_seapp_contexts（root 0644；app 读不到，adb_shell 能读）第 41 行：

user=_app minTargetSdkVersion=34 domain=untrusted_app_34 type=app_data_file levelFrom=all
  • 我们的进程：/proc/self/attr/current = u:r:untrusted_app_34:s0:c104,c256,c512,c768 → 命中 minTargetSdkVersion=34，且本 app 的 targetSdk 是 34。
  • type=app_data_file 就是"应用数据文件"的类型 —— 与前面 execve 被拒用同一个类型名。
  • levelFrom=all 生成了 c104,c256,c512,c768 这串 MLS 类别；ls -Z 里我们的文件带同样后缀，所以 同一个 app 的文件只有同一 app（同类别）能读，这是应用隔离的另一半。

三、seccomp 实测（本机）

  • /proc/self/status：Seccomp: 2、Seccomp_filters: 1 → 过滤器已生效（mode 2 = FILTER）。
  • 直接 exec 私有 ELF 的报错是 EACCES（Permission denied），不是 seccomp 的 EPERM/ENOSYS → 再次证明拦路的是 SELinux 的 entrypoint，不是 seccomp。

四、上游源码与本机的漂移（值得记一笔）

  • A15 源码 SetUpSeccompFilter()（com_android_internal_os_Zygote.cpp:639）按 uid 调 set_app_seccomp_filter() / set_system_seccomp_filter()，历史上策略来自文本文件 /system/etc/seccomp_policy/app.arm64.policy。
  • 本机 Android 17：该文件不存在；/system/etc/seccomp_policy/ 只剩 6 个（code_coverage、crash_dump、 mediacodec、mediaextractor）。实际提供者是 /system/lib64/libseccomp_policy.so（36 KB， 导出符号 set_app_seccomp_filter）。即策略从文本文件搬进了 so。

五、对"能不能在本机跑东西"的意义

  1. 我们的 app 永远是 untrusted_app_34 + app_data_file + 1 层 seccomp，改不了（无 root、无 BL）。
  2. execve 的拒绝来自 SELinux entrypoint；mmap 加载 OK —— 所以 /system/bin/linker64 <ET_DYN> 这条旁路在原理上是长期稳的，不是漏洞利用。
  3. 需要 fork/exec 子进程的工具（git 的 git-remote-https、pip、多进程命令行）在 app 身份下结构上不可行， 只能整条走 adb_shell（shell 域对 shell_data_file 有 entrypoint）。

四 · 附录：AOSP 源码怎么弄到手机上

日期：2026-11-06　机型：BKQ-AN20（荣耀Magic8 RSR 保时捷设计），SM8850，Android 17 / SDK 37，aarch64 环境：DSH app（uid 10104，untrusted_app_34）+ Shizuku shell（uid 2000）

结论

文章《一文搞掂Android AOSP的下载、编译、刷机》的三步，本机三步都不可行，但与 root 无关： 不可行的是①x86_64 Linux 编译主机 ②解锁 BL（刷机通道）③荣耀无 AOSP device tree / vendor blobs。 唯一可行的是"读源码"——但要换路径（GitHub codeload 的 tar 快照），不能用 repo/git 全量同步。

实测数据

1) USTC 镜像 git clone：失败（卡死）

  • 位置：https://mirrors.ustc.edu.cn/aosp/platform/{build,packages/apps/Settings,...}
  • 现象：ref advertisement 能拿到（manifest.git/info/refs 750 KB / 0.6 s），但 POST /git-upload-pack 之后 进度恒停在 119 KB，1–4 分钟无增长，HTTPS / HTTP / HTTP1.1 / 去掉 Expect 四种组合全都一样。
  • 判定：不是 TLS，不是快照深度，是链路（或镜像侧）对 fetch 流量的阻塞。

2) GitHub codeload tar 快照：可用（推荐）

  • 组织：aosp-mirror（100 个仓库，覆盖 frameworks/base、packages/apps/、system/、build/* 等主要项目）
  • 实测：
    • platform_packages_apps_Settings（main）：46.2 MB / 7.0 s（≈6.7 MB/s）→ 解压 167 MB / 8087 个文件
    • platform_system_core（main）：1.9 MB / 2.8 s → 解压 18 MB / 1810 个文件
    • 校验：src/com/android/settings/homepage/SettingsHomepageActivity.java 862 行，可 grep
  • 版本可选：tags 里有 android-12.1.0_r1（文章用的版本）、android-14.0.0_r1、android-15.0.0_r1， refs/tags 的 tarball 返回 200 application/x-gzip。
  • 脚本：$HOME/work/aosp-get.mjs node aosp-get.mjs packages/apps/Settings android-12.1.0_r1 ./a12 映射规则：<路径>/ → aosp-mirror/platform__

3) git 本身能在本机跑（但只能以 shell 身份）

  • app 身份：git clone 立即 fatal: cannot exec 'remote-https': Permission denied（SELinux 禁止 app 私有目录 execve）
  • shell 身份：把 termux prefix 复制到 /data/local/tmp/tp + 包装 /data/local/tmp/gitx.sh（设 GIT_EXEC_PATH/GIT_SSL_CAINFO） 后 git version 2.56.0 正常、helper 能 exec；失败原因是上面的镜像卡死，不是 git 本身。
  • 注意：CURL_CA_BUNDLE 不生效，必须用 GIT_SSL_CAINFO 指向 prefix/etc/tls/cert.pem。

4) 编译 / 刷机：硬墙

  • 官方要求 64 位 x86 主机 + 400 GB 空闲 + 64 GB 内存；本机 aarch64、无 apt、无 python/gcc/clang/java， AOSP host 工具全是 prebuilts/build-tools/linux-x86 的 x86_64 ELF，跑不了。
  • 内存：23.7 GB（可用 6.5 GB），已知 26 GiB + 4 GiB swap 的机器 -j2 仍被 oomd 杀。
  • BL：ro.boot.flash.locked=1、verifiedbootstate=green；荣耀官方（2026-04-25）明确不提供解锁码。
  • AOSP 只带 Pixel / goldfish / cuttlefish 设备配置，荣耀无 device tree / vendor blobs。
